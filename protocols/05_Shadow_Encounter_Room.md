## WHY IT'S BUILT THIS WAY

Three frameworks, each solving a different piece of "how do you build a
structured symbolic confrontation without a therapist in the room":

- **Active Imagination** (Jung; formalized as a practical 4-step method by
  Robert A. Johnson in *Inner Work*) — the actual Jungian technique for
  structured dialogue with unconscious material: **invitation → dialogue
  → values → ritual**. This isn't an analogy borrowed from somewhere
  else — it's the real methodology the Shadow Room is doing. It gives the
  session its shape.
- **Internal Family Systems (IFS)** — the principle that protective parts
  need to trust the process *before* vulnerable material gets approached,
  and that work only proceeds from a calm, curious, non-reactive stance
  (IFS calls this "Self-energy"). This isn't a clinical treatment being
  imported — it's the safety logic: **never go straight at the wound;
  get permission first; stay in a steady stance throughout.** This
  answers the gate: when is someone actually ready to enter this room.
- **Somatic Experiencing's titration and pendulation** (Peter Levine) —
  work in small doses, and deliberately rhythm between activation and
  safety rather than staying at intensity throughout. This answers
  pacing *inside* the room and shapes the exit.

None of these require Chelsey to be trauma-trained to apply — they're
structural rules about pacing and permission, not clinical assessment.

## ENTRY CRITERIA — WHAT DATA BUILDS THE ROOM

The Shadow Room is never generic. It's built from a pattern that already
qualifies as significant in Edin's own existing data model:

- The pattern must already meet the **loop definition** from the Crisis
  Escalation Protocol (`03_Crisis_Escalation_Protocol.md`, Track A): same
  tag/symbol cluster recurring across 3+ separate 14-day windows, with no
  resolved insight card, and flat-or-rising intensity. This reuses a
  definition that already exists rather than inventing a second
  threshold for "significant enough to confront."
- Inputs pulled for room-building, once a tag qualifies:
  - The `pattern_tags` history and `dream_narrative` text for that tag
    (Dream Methodology Spec)
  - `somatic_location` entries associated with that tag — the room should
    reference where the user has said they feel this in their body, not
    just the symbolic content
  - `emotional_intensity` trend for the tag (for pacing — see Titration
    below)
  - Any linked `insight_cards` already generated by the cross-modal
    engine for this tag (Cross-Modal Triggers Spec)
- **The Room is never auto-opened.** A qualifying pattern makes the Room
  *available* — Edin can name that it exists and invite the user toward
  it — but the user chooses to enter. This is the IFS "permission" logic
  applied structurally: the system doesn't drag anyone into confrontation.

**Access gate (IFS-derived safety rule):** the Room is not offered or
enterable in either of these states, regardless of whether a pattern
otherwise qualifies:
- Within some minimum cooldown window (draft: 72 hours — Chelsey to set)
  after a Crisis Escalation Track B event for that user
- During an active, freshly-flagged loop escalation that hasn't shown any
  stabilization yet (i.e., don't open the Room the same week a pattern
  first crosses into loop status — let it settle before confronting it)

## SESSION STRUCTURE — JOHNSON'S FOUR STEPS, ADAPTED

### 1. Invitation (entry / framing)

Edin names the pattern plainly and hands it back to the user as theirs,
not as an assignment: (draft, Chelsey to voice)

> "This one keeps returning — \[symbol/tag\], showing up \[N\] times over
> the last \[timeframe\], usually landing in \[somatic_location\]. It
> hasn't moved much on its own. If you're ready, we could meet it
> directly instead of circling it again. This is entirely your call — we
> don't have to."

No diagnostic language (per `04_DSM5_Jungian_Language_Line.md` — this
applies fully inside the Room, it does not get suspended for depth work).

### 2. Dialogue (the encounter itself) — paced by titration

The confrontation happens in **short exchanges, not one long
descent** — this is the titration principle applied directly. After each
exchange, Edin checks intensity before continuing (pendulation: contract,
then return toward safety, before going deeper again):

- Present the symbol/pattern back using the user's own language from
  their dream narratives — never Edin's interpretation imposed onto it.
- Ask what it wants, not what it means: Johnson's dialogue step is
  interaction, not analysis. ("What does this need from you right now?"
  rather than "What do you think this represents?")
- After every 1–2 exchanges, a explicit check-in beat: "Where's the
  intensity right now, compared to when we started?" If it's climbing
  past what the user came in with, pendulate back toward safety
  (grounding, breath, naming something steady) before either continuing
  or closing.
- **A visible, always-available exit is non-negotiable** — the user can
  leave the encounter at any point without completing it, framed as a
  legitimate choice, not a failure to finish.

### 3. Values (integration)

Johnson's ethical/values step: what does meeting this ask of the user
going forward, not just what did it say. Edin asks something like:
"Now that you've met this directly — what does it seem to be asking of
you? Not the meaning of it — what changes because you met it?"

### 4. Ritual (closing / exit)

A concrete closing action — Johnson's method is explicit that insight
without a physical/concrete ritual tends to slip back into the
unconscious ungrounded. This also serves as the deliberate return-to-
baseline beat from Somatic Experiencing — the Room does not end the
moment the dialogue ends.

- Edin proposes a small, concrete closing act (draft — specific rituals
  are content work, not methodology, and should come from Chelsey's
  existing practice library rather than being invented here)
- Edin explicitly marks the session as closed in its own language before
  handing the user back to the rest of the platform — no abrupt cutoff
- Session outcome logged (see Data Flow below) and referenced by Edin at
  the *next* relevant session — the Room's outcome doesn't disappear
  after the ritual, it becomes part of the ongoing pattern record

## SAFETY GUARDRAILS SPECIFIC TO THIS ROOM

- **Hard interrupt for crisis language**: if Tier 2/3 language (Crisis
  Escalation Protocol, Track B) appears at any point during a Room
  session, the Room immediately suspends — no ritual, no completion
  attempt — and Track B's override fires exactly as it would anywhere
  else in the app. Depth-work framing never delays or softens a crisis
  response.
- **No same-day re-entry after an early exit.** If the user leaves the
  encounter before the Values/Ritual steps, the Room doesn't reopen for
  that tag until the next day at the earliest — this prevents someone
  from repeatedly pushing back into unresolved intensity in one sitting,
  which is exactly what pendulation is designed to prevent.
- **Frequency cap** (draft): the Room is not something a user lives in —
  cap draft at one Room session per tag per 14-day period regardless of
  outcome, to keep this a deliberate confrontation rather than a
  recurring loop of its own.
- **Tenure gate** (open question, ties to Chelsey's own comment that
  "someone at a level of the work" carries this differently): should the
  Room be unavailable to brand-new users regardless of whether a pattern
  technically qualifies as a loop? Flagged below for sign-off — this
  matters because a new user's loop-qualifying pattern may reflect
  onboarding noise rather than real depth-work readiness.

## DATA FLOW / LOGGING

No new tables required — this reuses existing schema:

- A completed or exited Room session logs to `follow_through_log`
  (whether the user acted on/completed the encounter) and, where
  relevant, updates the linked `insight_cards.resolved` state for that
  tag.
- An early exit or a mid-session crisis interrupt logs to
  `flagged_events` the same way a Track B event would elsewhere, so
  Chelsey sees it in review regardless of where in the app it happened.
- The Room itself does not need a new table unless Chelsey wants
  Room-specific analytics (e.g., how many sessions per tag before
  resolution) — that's an implementation decision, not a methodology one.
